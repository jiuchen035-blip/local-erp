# 06 · AI 部分怎么跑：从聊天框到模型再到数据库

> 这一章讲清楚：用户打一句话进去，AI 是怎么"真去查数据库"并把答案拿回来的。
> 顺便：这段代码最大的特点是**没有用任何 AI 框架**，全手写，所以反而非常好读。

## 一、先搞清楚 AI 在这项目里能干什么

四个入口（前端 `AiChat.vue` 里的四个模式）：

| 模式 | 后端接口 | 干什么 |
|---|---|---|
| 智能助手 | `/api/ai/chat` | 会查数据、能开草稿单的 Agent（推荐，功能最全） |
| 智能开单 | `/api/ai/agent` | 只负责"帮我开一张采购单"这类；早期的入口，能力是 chat 的子集 |
| 知识库问答 | `/api/kb/ask` | RAG：先检索文档片段，再让模型照着答 |
| 查经营数据 | `/api/ai/query` | Text2SQL：把问题变成 SQL，查完再让模型说人话 |

外加一个隐藏能力：**AI 的身份是当前登录者**（草稿），AI 的所有写操作都会记进 `op_log`，
记录人写的是 `"AI·张三"`。

## 二、最核心的设计：一切向"OpenAI 兼容协议"看齐

### 什么是 OpenAI 兼容协议

OpenAI 当年定义了一套聊天的接口格式，后来**所有厂商都照抄了它**（这就是"兼容"）：

```
POST  https://某个地址/v1/chat/completions
Body: { "model":"模型名", "messages":[{role,content},...], "tools":[...] }
返回: { "choices":[ { "message":{ "role":"assistant","content":"...","tool_calls":[...] } } ] }
```

DeepSeek、智谱、通义、Kimi、硅基流动、本地 Ollama……**全都吃这一套**。

所以这个项目做了一件很聪明的事：

> **不接任何厂商 SDK，自己按这个格式发 HTTP 请求。**
> 于是"换成另一家模型"= "换个网址 + 换把钥匙"，代码一行不用改。

### 甚至把"网页版大模型"也包装成这个格式

这是这个项目最有创意的一节（第 2.3/2.4 节会讲）：
用 Python 起一个服务，假装自己是一个 OpenAI 接口，背后其实是开浏览器去网页上打字。

最终效果：

```
Java ModelClient  ──►  云端 API            （有 Key，最快）
                  ──►  本机 Ollama         （有显卡，免费）
                  ──►  Python 桥接 8317    （啥都没有，白嫖网页版）
```

**三种来源，一套代码。** 这就是全部设计的核心。

## 三、ModelClient：统一的插座

`ModelClient` 只有三个方法：

| 方法 | 干什么 |
|---|---|
| `chat(system, user)` | 简单一问一答，返回字符串 |
| `chatRaw(messages, tools)` | 完整对话，返回 assistant 消息对象（可能含 tool_calls） |
| `chatRaw(endpoint, messages, tools)` | 指定走某个来源（测试连接时用） |

核心代码：

```java
Map<String, Object> body = new LinkedHashMap<>();
body.put("model", ep.model());
body.put("messages", messages);
if (tools != null && !tools.isEmpty()) body.put("tools", tools);

Map<?, ?> resp = client(ep).post()
        .uri("/chat/completions")
        .body(body)
        .retrieve()
        .body(Map.class);
List<?> choices = (List<?>) resp.get("choices");
return (Map<String, Object>) ((Map<?, ?>) choices.get(0)).get("message");
```

注意 `baseUrl` 里已经带了 `/v1`（比如 `https://api.deepseek.com/v1`），所以这里拼的是 `/chat/completions`。

### 那行"看起来莫名其妙"的代码

```java
.requestFactory(new SimpleClientHttpRequestFactory())
```

**这行是救命的。** 原因记下来，这是全项目最贵的一个教训：

> Java 默认的 HTTP 客户端发 POST 时用的是 **chunked 分块编码 + 没有 Content-Length**。
> 云端厂商的服务器不在意，**但 Python 的 uvicorn 会把它当空请求体**，直接返回 422。
> 表现症状是："用 curl 测试一切正常，一用 Java 程序调用就报 Field required。"
>
> 换成 `SimpleClientHttpRequestFactory` 之后，请求会带上明确的 Content-Length 且走纯 HTTP/1.1，全部兼容。

> ⚠️ 顺带提醒：这里**没有设置任何超时**。网页版一轮可能要 7 分钟，
> 而 Tomcat 默认只有 200 个工作线程 —— 这是目前已知的性能隐患。

## 四、AiRouter：这次该用哪个模型？（自动降级）

比喻：你要发消息，手机优先用 WiFi，没 WiFi 就用流量，都没就用短信。

```java
public synchronized LlmEndpoint resolve(boolean ensureBridge) {
    // ① 用户明确要网页版 → 直接走
    if ("webchat".equals(provider)) return webEndpoint(ensureBridge);

    // ② 云端 Key 有效？（注意："在此填入你的API-KEY" 这种占位的也算无效）
    boolean hasKey = props.getApiKey() != null && !isBlank && !contains("填入");
    if (hasKey && 地址齐全 && 模型齐全) return new LlmEndpoint(provider, ...);

    // ③ 本机 Ollama 在线吗？（探测结果缓存 30 秒）
    String ollamaModel = probeOllama();
    if (ollamaModel != null) return new LlmEndpoint("ollama", "http://localhost:11434/v1", "", ...);

    // ④ 都不行 → 拉起 Python 桥接，白嫖网页版
    return webEndpoint(ensureBridge);
}
```

**三个巧妙的地方：**

1. **返回值是一个 `record`**（只有字段、没逻辑的小盒子），代表"这次用哪个端点"。
   **它不写回配置**，所以改设置立即生效、临时失败也不会污染设置。
2. **`lastFallbackReason`** 会记下"为什么降级了"，前端标签上悬停能看到原因
   （比如"当前厂家未配置有效 API Key，本地 Ollama 不在线，已自动降级到网页版模型"）。
3. **占位 Key 也判为无效** —— 因为它 yml 里的默认值就是 `"在此填入你的API-KEY"`，
   如果不判"填入"二字，默认配置会被误认为有效。

### Ollama 探测为什么要缓存 30 秒

```java
if (now - ollamaProbeAt < 30_000) return ollamaProbeResult;
```

因为它要发一次 HTTP 到本地 `11434`。一次 Agent 对话要循环 8 轮，
不缓存就是每轮都探测一次，白白浪费时间。

## 六、AgentService：AI 是怎么干活的

### 6.1 它是"工具箱 + 循环"，不是"聊天"

你问："可口可乐还剩多少瓶？"

AI 不是凭空回答，它是这样工作的：

```
第 1 轮：模型说 "我需要先查商品库" → 返回 tool_calls: search_products(关键词="可乐")
         Java 执行查库 → 拿到结果 → 拼回对话
第 2 轮：模型说 "我还需要知道库存" → tool_calls: low_stock() 或者直接从上一轮结果里算
第 3 轮：模型说 "好了，答案是 74 瓶" → 没有 tool_calls → 收工
```

**这就是所谓的 Agent。** 代码就是一个 for 循环：

```java
Map<String, Object> result = new LinkedHashMap<>();
for (int round = 0; round < 8; round++) {
    Map<String, Object> msg = modelClient.chatRaw(messages, tools());
    messages.add(new LinkedHashMap<>(msg));          // 把模型的回复记进对话

    Object callsObj = msg.get("tool_calls");
    if (!(callsObj instanceof List<?> calls) || calls.isEmpty()) {
        return ...;                                   // 没有工具调用 → 说明它给最终答案了
    }
    for (Object o : calls) {
        String name = 工具名;
        Map<String,Object> args = 参数;
        String r = om.writeValueAsString(dispatchTool(name, args));   // ★ 真正执行
        messages.add(Map.of("role","tool","tool_call_id", id, "content", r));
    }
}
return ...轮次用完的兜底文案;
```

**为什么上限 8 轮？** 防止模型陷入死循环（比如反复查询同一个东西），烧光你的 token。

### 6.3 安全边界（这段设计非常值得学）

```
┌──────────────── AI 能做什么 ────────────────┐
│ 查：所有经营数据（以登录者身份）             │
│ 写：只能创建"草稿"                          │
│ 禁止：过账、删除正式单据、改别人的数据       │
└─────────────────────────────────────────────┘
```

代码层面三重保险：

**① 身份注入**：把"你是张三、你是操作员"写进系统提示词

```java
String identity =
    "\n\n## 你的身份：\n" +
    "- 用户名：" + userLabel(用户名, userName) + "（“你”指的就是这个人）\n" +
    "- 角色：<操作人>（ADMIN=管理员；OPERATOR=操作员）\n" +
    "- 可访问菜单：" + String.join(" / ", allMenus) + "\n" +
    "- 数据来源：本系统的真实业务数据（SQLite），包括……\n";
```

**② 权限再卡一道**（和 HTTP 拦截器用同一份规则）

```java
if (!factory.isAdmin() && needAdmin.containsKey(name)) {
    if (!AccessRules.allowTool(role, true)) return Map.of("error", AccessRules.denyReason(role, true));
}
```

**③ 所有写操作都审计**

```java
aiAuditService.record(userLabel(用户名, userName), name, args.toString(0,0,400));
```

> 一句话总结：**AI 最多把事情做到"草稿"为止，最后拍板的一定是人。**
> 模型幻觉最多到草稿为止，不会真的把账搞乱。这是这个项目 AI 部分最专业的一处设计。

### 6.4 草稿怎么回到前端

`create_draft_bill` 的返回值里带了单据信息，`AgentService.run` 把它摘出来放进 `draft` 字段：

```java
if ("create_draft_bill".equals(name)) draft = cleanDraft(out);
else if ("create_peer_draft".equals(name)) { draft = out; draft.remove("purchaseId"); }
```

前端 `AiChat.vue` 收到 `r.draft` 就渲染一张"确认过账"卡片：

```js
async function postDraft(m) {
  const r = m.draft.peerPurchaseId ? await api.postWithPeer(m.draft.id) : await api.postBill(m.draft.id)
  ElMessage.success(r.message)
  m.text += '\n✅ 草稿 ' + m.draft.billNo + ' 已过账'
  m.draft = null
}
```

**这就是"人机协同"的闭环**：AI 提议 → 人类点确认 → 走的是和手工开单完全相同的 `BillService.post`。
没有第二套逻辑，所以不可能出现"AI 开的单和手工开的单规则不一样"。

### 6.5 `create_draft_bill` 里那些"看起来啰嗦"的校验

```java
if (i.getProductId() == null) missing.add("第" + (idx+1) + "行缺 productId");
if (i.getQuantity() == null || i.getQuantity() <= 0) missing.add("第" + (idx+1) + "行 quantity 必须>0");
if (bill == null) missing.add("第" + (idx+1) + "行商品不存在 productId=" + i.getProductId());
if ("TRANSFER".equals(type) && t == null) missing.add("TRANSFER 必须传 warehouseId 和 toWarehouseId，且两者不能相同");
if (bill != null && !"DRAFT".equals(bill.getStatus())) continue;   // 草稿不能直接确认，返回 id 给前端
```

**为什么要收集"第几行缺什么"并返回，而不是直接抛异常？**
因为模型的"输入"是从文本解析来的，很容易少字段。告诉它具体哪行错了，
**它下一轮会自己修正**（这是 Agent 的典型 self-correction）。如果直接抛异常，它只能放弃。

同理，模型偶尔会传"商品名"而不是"ID"，代码也给了兜底：

```java
if (i.getProductId() == null && i.getProductName() != null && !i.getProductName().isBlank())
    missing.add("第" + n + "行需要传 productId（数字），请先用 search_products 查到准确商品，"
              + "确认同名后重试；接口不支持以名称代填");
```

### 6.6 `query_data`：最强大也最危险的工具

```java
int pos = 0;
for (String cursed : FORBIDDEN) {              // 12 个黑名单关键词
    int hit = sql.toUpperCase().indexOf(cursed.toUpperCase(), pos);
    if (hit >= 0) {
        String guess = ...;
        return Map.of("error", "只允许只读查询，已拦截可能相关的结构：" + guess + "。"
                             + "如需编程式功能请明确区分“写代码”和“执行写操作”后再请求");
    }
}
if (!sql.toUpperCase().startsWith("SELECT")) return Map.of("error", "仅允许单条 SELECT 语句；不支持 WITH(CTE)、INSERT、UPDATE、DELETE、DROP、ATTACH、PRAGMA 等结构。");
try {
    rs = stmt.executeQuery(sql);
    ...一直 rs.next()，超过 200 行就跳出上限预警...
} finally { try { if (stmt != null) stmt.close(); } catch (SQLException ignored) {} }
```

防护措施：黑名单关键词 + 必须以 SELECT 开头 + 200 行上限 + finally 里关 Statement。

> ⚠️ **它没有限制"能查哪些表"**。理论上模型可以写 `SELECT * FROM sys_user`，
> 表里是**所有用户的密码哈希**，而这个结果会随对话发给你选的云端厂商。
> 这是目前 AI 安全最大的缺口，建议第一优先级加上"表白名单"。

## 七、Text2SQL：`/api/ai/query`

两跳式设计（先模型→再查库→再模型）：

```java
// 第 1 跳：让模型写 SQL
String sql = modelClient.chat("你是SQL生成器……只允许 SELECT……" + SCHEMA, question)
        .trim().replaceAll("(?i)^```(sql)?|```$", "").trim();   // 去掉 markdown 代码块围栏

// 安全闸门
if (!sql.toUpperCase().startsWith("SELECT")) return Map.of("sql", sql, "error", "仅允许只读查询");

// 执行
var rows = jdbcTemplate.queryForList(sql);

// 第 2 跳：让模型把结果说成人话
String summary = modelClient.chat("你是经营分析助手……用两三句中文给商家解释结论……", rows.toString());
return Map.of("sql", sql, "rows", rows, "summary", summary);
```

**为什么把 SQL 也返回给前端？** 让懂行的人能看到它到底查了什么 —— 可解释性。

> ⚠️ 这个入口没有 200 行上限，和 Agent 侧的 `query_data` 不一致（已知小问题）。

## 八、RAG：知识库问答

```
用户提问
  ↓
KbService.search(问题, topK=4)   →  找出最相关的 4 段文档片段
  ↓
拼成上下文："【来源:xxx】\n内容……"
  ↓
喂给模型，并明确要求"答案后用（来源：xxx）标注；知识库没有的信息就明确说不知道，不要编造"
  ↓
返回 {answer, sources}
```

**没配模型时**退化成直接把检索到的原文贴出来：

```java
if (!aiProps.chatConfigured()) {
    return Map.of("answer", "【未配置模型 API-KEY，仅返回检索结果】\n" + 各片段原文, "sources", sources);
}
```

> 这个降级思路贯穿全项目：**没有某个条件时，功能降级但不停摆。**
> 同理：没有 embedding 模型 → 关键词检索；没有 Key → Ollama；都没有 → 网页版。

## 九、Python 桥接：把网页版大模型包装成 API

### 整体结构

```
webllm/
├─ server.py          FastAPI 服务，暴露 /health、/v1/models、/v1/chat/completions、/login/{site}
├─ toolcall.py        工具定义 ↔ 文本协议，双向转换
├─ browser.py         管理 Playwright 浏览器与每站点的锁
└─ adapters/
   ├─ base.py         适配器基类
   ├─ deepseek_web.py DeepSeek 网页
   └─ miaoxiang.py    东方财富妙想
```

### 关键一：如何让不支持 Function Calling 的模型支持工具调用

思路是**文本协议**。请求侧把工具清单渲染成人话：

```
工具：search_products
功能：按名称/条码检索商品
参数：
  - keyword（string）：商品名称关键词
```

并规定输出格式：

```
如果需要调用工具，请在回复中严格按以下格式返回：
<tool_call>
{"name": "工具名称", "arguments": {...}}
</tool_call>
```

响应侧用正则抠出来，重组成标准的 OpenAI `tool_calls`：

```python
_TOOL_CALL_RE = re.compile(r"<tool_call>\s*(\{.*?\})\s*</tool_call>", re.DOTALL)
raw = re.sub(r",\s*([}\]])", r"\1", raw.strip())     # 容错：模型经常输出尾逗号
```

**上层的 Java Agent 循环对此完全无感** —— 它收到的是标准格式。这是很漂亮的一层抽象。

### 关键二：prompt 的顺序不能乱

```python
parts = []
if sys_parts:    parts.append("【系统设定】\n" + ...)     # 1
if tools_prompt: parts.append("【可用工具参考】...")
parts.extend(dialog)                                     # 2 历史
parts.append("现在直接处理上面最后一个用户请求：……")      # 3 指令永远放最后
```

> 踩过的坑：工具说明放在最前面时，网页模型把它当成任务本身，
> 于是它复述一遍工具清单就交差了，真正的问题没处理。
> **对网页模型来说，最后一条消息才是任务焦点。**

### 关键三：每次请求都重新打开网页会话

```python
await goto_site(page, adapter)      # 每次都 goto 首页
await adapter.chat(page, prompt)
```

> 否则网页上残留着上一轮的对话，模型看到的上下文是乱的。
> 这叫"由调用方保证无状态"。

### 关键四：回答什么时候算结束

## 十、动手：给 AI 加一个新工具

这是掌握 AI 部分最好的练习。**三步：**

### 第 1 步：写业务方法（`AgentService` 内）

```java
private Map<String, Object> myNewTool(Map<String, Object> args) {
    String kw = String.valueOf(args.getOrDefault("keyword", ""));
    // ...用 mapper 查库...
    Map<String, Object> r = new LinkedHashMap<>();
    r.put("ok", true);
    r.put("rows", 结果列表);
    return r;
}
```

### 第 2 步：注册工具定义（`tools()` 方法里加一项）

```java
 Map.of(
   "type","function",
   "function", Map.of(
     "name","my_new_tool",
     "description","一句话说明这个工具干什么（模型靠这句话决定要不要用）",
     "parameters", Map.of(
       "type","object",
       "properties", Map.of(
         "keyword", Map.of("type","string","description","商品名称关键词")
       ),
       "required", List.of("keyword")   // ⚠️ 忘了这里模型就不传
     )
   )
 )
```

### 第 3 步：挂到分发（`@ToolMethod` 注解 + `dispatchTool`）

```java
@ToolMethod(value = "my_new_tool", desc = "一句话说明", required = {"keyword"})
public ToolResult myNewTool(com.fasterxml.jackson.databind.JsonNode args) { ... }
```

> **写 description 是最重要的一步。** 模型不是靠代码理解你的工具，
> 它是**读你写的这段话**来决定要不要调用。写得含糊，它就永远不会用或者乱用。
>
> 另外：如果是写操作而且只想给管理员用，记得加到 `needAdmin` 集合里。
