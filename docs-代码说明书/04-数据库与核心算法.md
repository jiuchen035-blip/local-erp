# 04 · 数据库与核心算法：数字是怎么算出来的

> 这一章是全篇最重要的：**看懂了这些算式，你就能改任何业务规则。**
> 我们一个从业三十年的会计都会同意的做法出发，配上真实数字算一遍。

---

## 一、先认识 SQLite

### 它是什么

一个**不需要安装、不需要启动服务**的数据库。它就是一个文件：

```
backend/data/erp.db     ← 这就是全部数据
```

- 想备份？**复制这个文件**
- 想重置全部数据？**删掉 `data` 文件夹，重启程序**
- 想看看里面有什么？下载免费的 **DB Browser for SQLite**，打开这个文件

> MySQL 要装服务、要建账号、要开端口 —— 对发给小店老板的软件来说，这些都是灾难。
> SQLite 让"安装这个软件"变成"解压这个文件夹"。

### 它和数据这包括什么

```
data/
├─ erp.db                   主数据库（18 张表）
├─ ai-settings.json         AI 配置（比你 yml 里填的优先级高）
├─ images/12.png            商品图片，按商品 id 命名
├─ webllm-profiles/         网页模型的登录态
└─ logs/local-erp.log       运行日志
```

## 二、18 张表，用人话分组

### 第一组：做生意的核心（重点看！）

| 表名 | 人话 | 关键字段 |
|---|---|---|
| **product** | 商品档案：叫什么、多少钱 | `name` `sku` `sale_price` `cost_price` `avg_cost`(平均进价) `barcode`(扫码枪用) |
| **warehouse** | 仓库：前店、后库 | `name` |
| **bill** | 单据主表：一张单的头（谁、哪个仓、多少钱、草稿还是已过账） | `bill_no` `type` `status` `paid` `discount` `total_amount` |
| **bill_item** | 单据明细：一行一个商品 | `bill_id` `product_id` `quantity` `price` `batch_no` |
| **stock_record** ★ | **流水账本，全系统的核心** | `product_id` `quantity`(带正负) `price` `cost_price` `paid` `warehouse_id` |

> **为什么单据要拆成两张表？**
> 一张单据有头（日期、供应商、总金额）和行（买了什么）。行数不确定，塞在一张表里会有大量重复。
> 拆开是数据库的经典做法，`bill.id = bill_item.bill_id` 把它们连起来。

### 第二组：人来人往

| 表名 | 人话 |
|---|---|
| **partner** | 供应商和客户都存在这张表，靠 `type` 字段区分（SUPPLIER / CUSTOMER）；还有开业时的"期初欠款"字段 |
| **ledger** | 预留的往来账表（实际应收应付是从流水实时算的，这张基本没用到） |

### 第三组：人和管理

| **sys_user** | 登录账号，密码是 BCrypt 加密后的（看不出原文），`role` 区分 ADMIN / OPERATOR |
| **op_log** | 操作日志。HTTP 层自动记，AI 也会记（记录人写成"AI·用户名"） |

### 第四组：行业专用

| **inspection** | 灭火器年检档案（这个项目给消防器材店做的）。记录客户、电话、下次到期日 `next_date` |

### 第五组：知识库（给 AI 用）

| **kb_document** | 一篇文档 |
| **kb_chunk** | 文档切成的片段（约 500 字一段），还有一列存向量（一串数字，用来做语义搜索） |

### 第六组：财务会计

| **account** | 会计科目表（库存现金、应收账款、主营业务收入……），预置 17 个常用的 |
| **voucher** | 记账凭证的头（凭证号、日期、来源） |
| **voucher_item** | 凭证的分录（借什么科目、贷什么科目、多少钱） |

### 第七组：电商和同行

| **peer_stock** | 同行的货源目录（从隔壁店能调到的货） |
| **integration_channel** | 淘宝/拼多多等平台的配置（目前只存配置，还没真对接 API） |
| **platform_order** | 导入过的电商订单，用"平台 + 平台单号"做唯一约束防止重复导入 |

## 三、五条字段约定（背下来，代码就通了）

### 1. `bill.type` —— 单据有 7 种脸

`PURCHASE`(进) `SALE`(卖) `PURCHASE_RETURN`(退给供货商) `SALE_RETURN`(顾客退)
`LOSS`(报损) `GAIN`(盘盈) `TRANSFER`(调拨)

### 2. `bill.status` —— 只有两个状态

`DRAFT` 草稿（**不动库存**）/ `POSTED` 已过账（**动了库存，不可逆**）

### 3. `stock_record.quantity` —— 带正负号

- **正数** = 入库（货多起来了）
- **负数** = 出库（货少了）

> 记住：**流水类型只有三种**（`PURCHASE`/`SALE`/`ADJUST`），但单据有七种。
> 7 → 3 → 正负号 的转换发生在 `BillService.insertRecord` 里：
> ```java
> r.setType(signedQty > 0 ? "PURCHASE" : "SALE");
> r.setQuantity(signedQty);
> ```

### 4. `stock_record.paid` —— 1 现结 / 0 挂账

这一条决定它进不进"应收应付"。挂账的销售 = 客户欠我钱；挂账的采购 = 我欠供货商钱。

### 5. `stock_record.cost_price` —— 这一笔的成本快照

卖出的时候，把"当前的平均进价"抄一份存在这条流水上。**为什么要用快照？**
因为平均进价以后还会变。如果以后直接回头查商品表，历史毛利润会跟着被重新计算，账就对不上了。

## 四、核心算法一：库存就是把流水加起来

```java
public Map<Long, Integer> currentStock() {
    Map<Long, Integer> stock = new HashMap<>();
    for (StockRecord r : recordMapper.selectList(null)) {          // 把所有流水捞出来
        stock.merge(r.getProductId(), r.getQuantity(), Integer::sum);  // 按商品累加
    }
    return stock;
}
```

**举个真实的例子**，假设可乐的流水本长这样：

| 时间 | 单据 | 数量 | 累计库存 |
|---|---|---|---|
| 9/1 | 采购入库 | +100 | 100 |
| 9/3 | 销售出库 | −20 | 80 |
| 9/5 | 销售出库 | −5 | 75 |
| 9/8 | 顾客退货 | +2 | 77 |
| 9/10 | 盘点报损 | −3 | **74** ← 这就是当前库存 |

商品表里**根本没有"库存"这一列**。74 是把这些数字加起来得到的。

### 为什么要这么麻烦

假设老板说"我明明记得有 80 瓶，怎么变成 74 了"？
如果只存一个数字，你查不出来。有了流水本，你能指着说：
"9/5 卖了 5 瓶给张三，9/10 盘点发现少了 3 瓶，是我们的 XXX 流程出问题了。"

**代价**：每次查库存都要翻完所有流水。数据量小的时候完全没问题（几万条就是毫秒级），
这也是为什么作者敢这么写。详见优化清单里第 5 条改成 `GROUP BY`。

### 分仓库版本

`stockByWarehouse()` 逻辑一样，只是多了一层 **仓库 → 商品 → 数量** 的嵌套：

```java
result.computeIfAbsent(warehouseId, k -> new HashMap<>())
      .merge(r.getProductId(), r.getQuantity(), Integer::sum);
```

读到这里有个细节值得注意：`r.getWarehouseId() == null ? 0L : r.getWarehouseId()`，
老数据没有仓库字段的（历史流水）统一归到 0 号，不会因为空指针崩掉。
**这种"给历史数据兜底"的处理在整个项目里随处可见，是单机软件升级不留祸的典型做法。**

## 五、核心算法二：移动加权平均成本（进价怎么算）

### 为什么要算"平均"？

同一批可乐，你可能这次进是 3 块，上次进是 2.5 块。
卖出一瓶的时候，它的成本到底是 3 还是 2.5？

现实的做法是：**放在一起算个平均数**。这就是"移动加权平均法"（小企业会计准则允许的最简单方法）。

### 公式

```
新的平均进价 = (原来的平均进价 × 原来有多少 + 这次的单价 × 这次进了多少) ÷ (原来有多少 + 这次进了多少)
```

### 真实过一遍数字

假设：仓库里有 **20 瓶**可乐，平均进价 **2.5 元/瓶**。
现在又进了 **100 瓶**，单价 **3.0 元/瓶**。

```
        分子 = 2.5 × 20 + 3.0 × 100 = 50 + 300 = 350
        分母 = 20 + 100 = 120
        新的平均进价 = 350 ÷ 120 = 2.9167 元/瓶
```

代码（`BillService.post` 第 265-279 行）：

```java
if ("PURCHASE".equals(type)) {
    double netUnit = effPrice;
    if (financeSettings.get().isTaxEnabled()) {          // 开了计税，用不含税价算成本
        netUnit = round2(effPrice / (1 + rate / 100));
    }
    int curTotal = Math.max(stockService.currentStock().getOrDefault(item.getProductId(), 0), 0);
    double newAvg = (avgCost * curTotal + item.getQuantity() * netUnit)
                    / (curTotal + item.getQuantity());
    p.setAvgCost(Math.round(newAvg * 10000) / 10000.0);   // 保留 4 位小数
    productMapper.updateById(p);
    avgCost = p.getAvgCost();                             // 后面的流水用新均价做快照
}
```

**注意最后一行**：算完之后立刻更新局部变量 `avgCost`，因为同一张单如果还有第二行是同一个商品，
要用最新的均价。

### 为什么要保留 4 位小数而不是 2 位？

因为钱是能算到分的（2 位），但单价往往是 2.9167 这种无限不循环的数字。
**单价多留两位精度，最终金额再四舍五入**，累积误差才小。这叫"精度预留"。

### 再算一遍毛利

上面那批可乐，现在以 **4 元/瓶** 卖出 5 瓶：

```
销售额     = 4 × 5         = 20.00 元
结转成本   = 2.9167 × 5    = 14.58 元
毛利       = 20.00 − 14.58 = 5.42 元
```

代码里结转时把当时的均价抄进流水：

```java
r.setCostPrice(avgCost);
```

> **重要提醒**：只有销售类流水才计入毛利。
> 调拨（换个仓库）、报损、盘盈都不算"做生意"，不进经营流水。

## 六、核心算法三：整单折扣怎么分摊（很妙的一招）

老板说"这张单给你打个 95 折"。这个折扣是**整张单**的，但库存流水、成本核算是**按商品行**算的。
怎么办？答案是：**把折扣摊到每一行上**。

```java
double effPrice = round2(item.getPrice() * disc / 100);
```

举例：单上有两行，一行 100 元的 A，一行 50 元的 B，整单 95 折：

| 商品 | 原价 | 折后单价（effPrice） | 行小计 |
|---|---|---|---|
| A（2 件） | 100 | 95.00 | 190.00 |
| B（1 件） | 50 | 47.50 | 47.50 |
| **合计** | | | **237.50**（= 250 × 0.95 ✓） |

**关键在这句话之后的每一行代码**：
库存流水的 `price`、结转的成本、应收应付的金额，**全部用 `effPrice` 而不是原价**。

```java
insertRecord(bill, item, effPrice, signed, avgCost);
```

> 这就是为什么"单据上的总金额"永远等于"账上收到的钱"。
> 聪明的做法：**找一个唯一的"实际成交单价"，让所有地方都用它。**

## 七、核心算法四：价税分离（可选功能）

如果开了计税，老板看到的 100 元是**含税价**。会计入账要拆成"销售额 + 税":

```
含税价 ÷ (1 + 税率) = 不含税销售额
差额就是税
```

例：含税 113 元，税率 13% → 不含税 100 元，税 13 元。

生成凭证时会**按税率分组**：不同税率的商品各自生成一条收入分录和一条税额分录。

```java
if (taxOn) {
    for (var e : byRate.entrySet()) {                 // byRate: 税率 → [金额合计, 数量合计]
        double net = splitNet(e.getValue()[0], e.getKey());
        addTaxItem(items, "6001", "CREDIT", net, "销售收入", e.getKey(), e.getValue()[1]);
        addTaxItem(items, "2221", "CREDIT", r2(e.getValue()[0] - net), "销项税额", e.getKey(), null);
    }
}
```

**为什么按税率分组？** 因为中国的增值税是多档税率（13%、9%、6%），
一张单上可能有 13% 的百货和 9% 的食品，必须分开申报。

## 八、核心算法五：冲正（怎么优雅地撤销）

场景：老板上周把"进了 100 瓶"错写成"进了 10 瓶"并过了账。

**错误的做法**：直接改那张单的数字，或者直接删掉。→ 账断了，审计通不过。

**这个项目的做法**（`BillService.reverse`）：

1. 查出原单，类型换成"相反的那一种"
2. 数量价格照抄，生成一张新单（状态是草稿）
3. 备注写成 `"冲正#原单号"`，永久留痕
4. **立刻过账** → 产生反向流水 → 库存回到正确值
5. 如果原单是赊账的，把原单和它的流水都标成"已结清"
6. **原单一字不改地留着**

```java
private static final Map<String, String> REVERSE_TYPE = Map.of(
    "PURCHASE", "PURCHASE_RETURN",  "PURCHASE_RETURN", "PURCHASE",
    "SALE",     "SALE_RETURN",      "SALE_RETURN",     "SALE",
    "LOSS",     "GAIN",             "GAIN",            "LOSS",
    "TRANSFER", "TRANSFER");
```

**调拨单要特别处理**：它的出仓和入仓是反的，所以:

```java
rev.setWarehouseId("TRANSFER".equals(origin.getType()) ? origin.getToWarehouseId() : origin.getWarehouseId());
rev.setToWarehouseId("TRANSFER".equals(origin.getType()) ? origin.getWarehouseId() : null);
```

翻译成人话：**冲一张调拨单时，要把"从哪到哪"倒过来**。

还有一道保险，防止无限套娃：

```java
if (origin.getRemark() != null && origin.getRemark().startsWith("冲正#"))
    throw new IllegalArgumentException("冲正单不能再冲正");
```

## 九、核心算法六：盘点（差异自动成单）

盘点的流程：

1. 系统列出每个商品在仓库里的**账面库存**（用上面的方法算的）
2. 老板一行行填**实际数**
3. 点提交，系统只处理**有差异的行**：

```
实际 > 账面  →  自动生成一张"盘盈单(GAIN)" 并过账，补充差的那部分
实际 < 账面  →  自动生成一张"报损单(LOSS)" 并过账，扣掉多的那部分
```

**为什么自动生成单据而不是直接改库存？** 因为铁律一：**改库存的唯一合法途径是流水**。
生成单据 = 生成流水 = 可追溯。

金额按当前平均进价算，所以盘点**不影响毛利**（这是刻意的，盘点不是做生意）。

## 十、应收应付是怎么实时算出来的

老板问："张三还欠我多少钱？"

答案不是存在某张表里的，是这样算出来的：

```
张三的期初欠款（partner.opening_receivable）
+ 所有"挂账(paid=0)的销售流水"金额总额
− 已经核销掉的部分(record.settled_at 不为空)
```

所以你会发现：

- **没有"应收账款"这张表**
- 它永远是实时算出来的
- 结清 = 把那些流水标成已结，或者直接插入一条反向流水

> 这也是为什么"应收应付"页面永远是准的：**它不可能和流水对不上，因为它就是流水本身。**

## 十一、自己动手验证：怎么看数据

1. 下载 [DB Browser for SQLite](https://sqlitebrowser.org/)（免费）
2. 打开 `backend/data/erp.db`
3. 点"浏览数据"，选 `stock_record` 表 → **你看到的每一行就是一笔流水**
4. 想验证库存？执行这条：

```sql
SELECT product_id, SUM(quantity) AS 库存
FROM stock_record
GROUP BY product_id;
```

拿这个结果和软件界面上的库存对比 —— **一定是一样的**，因为软件就是这么算的。

> 敢动手跑 SELECT 是安全的。**不要直接 UPDATE / DELETE**，改数据请通过软件界面。
> 万一写坏了：删掉 `data` 文件夹重启，或者从 `backup/` 里恢复。
